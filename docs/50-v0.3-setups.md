# 50 — v0.3 — Setups (the shareable unit)

v0.1 built a pull/apply loop for `settings.reader.lua`. v0.2 built a
snapshot/restore loop for the stuff YAML doesn't cover. v0.3 turns
those primitives into a **shareable artifact**: a *Setup* — a named,
versioned, content-hashed manifest that Alice can export from her
Kindle and Bob can import onto his, safely and smoothly.

Setups are the data model everything else in v1 binds to: the
frontend (v0.7) renders them, compat checks (v0.4) validate them,
distribution (v0.5) moves them around. Get this layer right and the
rest is plumbing.

## Design principles

Three user-directed rules that shape every decision below:

1. **When in doubt, surface a switch.** If two reasonable defaults exist,
   pick one and expose a flag for the other. No silent choices.
2. **Don't babysit the user.** We do not limit capabilities (plugin
   files, arbitrary Lua patches, full replace-not-merge) to protect
   users from themselves. We *disclose* what a Setup does, loudly and
   specifically, and trust adults to decide.
3. **Streamlined default + advanced opt-in.** Every command has a
   sensible default for the ordinary case and a flag (or UI toggle) for
   the advanced case. Never force an advanced user into a dumbed-down
   path; never force a new user to think about advanced concerns.

## Goal

After v0.3:

- Alice: `kindly setup export night-reading --output night.kset` produces
  a file that describes her setup. She uploads it to Reddit.
- Bob: `kindly setup import night.kset --dry-run` shows him exactly
  what will change. `kindly setup import night.kset` applies it, with
  a safety snapshot, merging non-destructively unless the Setup
  explicitly says otherwise.
- Rollback: whatever was on Bob's device before import is in
  `.kindly/pre-restore/<iso>.tar.gz`. One command puts it back.

## Scope decisions

| # | Question | Decision |
|---|----------|----------|
| S1 | Setup file format? | YAML manifest. For Setups that ship plugin dirs or patch files, package as a zip with `manifest.yaml` at the root (a "fat" setup). Pure-settings Setups stay as a single YAML file ("lean" setup). File extension: `.kset` (zip) or `.kset.yaml` (lean). |
| S2 | Setup identity? | **Content hash.** SHA-256 of canonicalized manifest bytes (lean) or of the zip with a stable file order (fat). First 12 hex chars used as short ID for display. Human-readable `name` field is for humans; hash is for trust/pinning. |
| S3 | What's shareable? | Everything that meaningfully travels: `settings.reader.lua` keys (filtered for secrets), `plugins_disabled` toggles, full plugin directories, `patches/*.lua` files, `defaults.custom.lua`. Nothing is excluded for paternalistic reasons. Risky items are disclosed, not blocked. |
| S4 | Secrets in exported Setups? | Filtered out by the existing v0.1 denylist. Alice physically cannot ship her PIN in a shared Setup. This is a safety invariant, not a paternalism call. |
| S5 | Apply mode? | `additive` (merge onto existing config — v0.1 semantics) OR `replace` (wipe non-declared keys first, then merge). Author declares in manifest; importer sees it in the preview. Default: `additive`. |
| S6 | Plugin/patch import risk? | Plugin files and patches are arbitrary Lua code. Import is **allowed** by default but gated on explicit flags (`--accept-plugins`, `--accept-patches`) OR a user confirmation in interactive/UI mode. The confirmation is an *informed disclosure*, not a gatekeeper — "this Setup contains 3 patches totaling 12KB of Lua that will execute on your device; proceed?" |
| S7 | Schema versioning? | Required from day one. Every manifest declares `kindly_setup: v1`. Future breaking changes bump this; importers refuse unknown major versions with a clear message ("this Setup requires kindly 0.5+"). |
| S8 | Compatibility metadata? | Every Setup declares `koreader_version_min/max` (optional) and `device` (optional, free-form list). Enforcement is v0.4's job; v0.3 stores and displays these fields. |
| S9 | How are Setups stored locally? | `~/.kindly/setups/<short-id>-<name-slug>.kset(.yaml)`. `kindly setup list` enumerates them. Exports default to this dir unless `--output` overrides. |
| S10 | Templates / curated starting points? | `kindly setup export --template <name>` copies a known curated key-set (e.g. `night-reading`, `minimal-ui`, `heavy-annotation`) from device state. Templates ship inside the kindly binary as a small registry. Editable after export. |

## Non-goals for v0.3

- **Discovery infrastructure.** No central registry, no accounts, no
  server. A Setup is a file; sharing happens out-of-band (gist, Reddit,
  email, USB). v0.5 adds `kindly setup import <url>` that fetches a
  public URL — no more.
- **Highlights / `.sdr/` sync.** Orthogonal to sharing (nobody shares
  bookmarks). Personal backup, shipping in v0.6.
- **Frontend/GUI.** CLI only in v0.3. UI in v0.7 once the data model is
  frozen.
- **Setup merge / combine / inheritance.** "Alice's night-reading Setup
  +  Bob's minimal-UI Setup" is a real want but a schema problem.
  Deferred.
- **Signature / trust infrastructure.** A Setup's author field is free
  text; we don't verify it. Content hash lets people pin a known-good
  version ("I trust this specific hash"), which is enough trust machinery
  for v0.3. Signed Setups can layer on later without breaking the format.

## Manifest schema (v1)

Canonical YAML, 2-space indent, keys sorted lexicographically for
hashing. Example (lean setup):

```yaml
kindly_setup: v1

meta:
  name: "Night Reading — PW5"
  author: "alice"                    # free text, not verified
  description: "Low flashing, warm light, minimal UI chrome"
  created_at: "2026-04-21T12:00:00Z"
  tags: [night, minimal, pw5]

compat:
  koreader_version_min: "2024.03"
  koreader_version_max: null         # null = any
  device: [kindle-pw5]               # free-form, null/missing = any

apply_mode: additive                 # additive | replace

settings:                            # filtered settings.reader.lua keys
  avoid_flashing_ui: true
  inertial_scroll: false
  night_mode: true
  screen_warmth: 60

plugins:
  disabled: [coverbrowser, statistics]  # toggle, no files shipped
  # `files:` absent → lean setup
```

Fat setup adds a `files:` block under `plugins:` and/or a `patches:`
block, referring to paths inside the zip:

```yaml
plugins:
  disabled: [coverbrowser]
  files:
    - path: plugins/SSH.koplugin
      hash: sha256:a1b2...
      bytes: 48231

patches:
  - path: patches/2-autoflash.lua
    hash: sha256:c3d4...
    bytes: 412
    description: "Force a full refresh every 6 pages"
```

The zip layout for a fat setup:

```
mysetup.kset                 (zip file)
├── manifest.yaml
├── plugins/
│   └── SSH.koplugin/
│       ├── main.lua
│       └── ...
└── patches/
    └── 2-autoflash.lua
```

### Required vs optional fields

Required: `kindly_setup`, `meta.name`, `meta.created_at`, `apply_mode`.
Everything else is optional. Importer fills in sensible defaults on
missing fields (empty settings, no plugins, no compat constraint).

### Canonicalization rules (for content hashing)

- YAML dumped with: 2-space indent, keys lexicographically sorted at
  every level, flow-style sequences forbidden, trailing newline.
- Strings double-quoted only when necessary (YAML's default heuristic).
- For fat setups: zip file order is manifest first, then remaining
  entries sorted by path; timestamps zeroed; permissions normalized.

## Commands (CLI surface for v0.3)

```
kindly setup export <name>
    [--output <path>]                  # default: ~/.kindly/setups/<id>-<slug>.kset[.yaml]
    [--keys <k1,k2,...>]               # cherry-pick specific settings keys; default: all filtered keys
    [--template <name>]                # start from a curated key-set
    [--include-plugin-files]           # ship .koplugin dirs (fat setup)
    [--include-patches]                # ship patches/*.lua (fat setup)
    [--apply-mode additive|replace]    # default: additive
    [--description <text>]
    [--tags <t1,t2,...>]
    [--mount <path>]

kindly setup import <file>             # <file> can be local path; v0.5 adds URLs
    [--dry-run]                        # preview only, no writes
    [--no-safety-snapshot]             # skip pre-apply snapshot (reuses restore flag)
    [--accept-plugins]                 # required to install shipped plugin dirs
    [--accept-patches]                 # required to install shipped patch files
    [--force-compat]                   # override koreader_version_min/max mismatch
    [--mount <path>]

kindly setup inspect <file>            # print manifest + summary, no device touch
kindly setup list                      # list ~/.kindly/setups/
kindly setup hash <file>               # print canonical content hash (for pinning/verification)
```

All destructive operations preview before acting and take a safety
snapshot by default (same mechanism as `kindly restore`).

## What we reuse from v0.1 / v0.2

Nothing here is reimplemented — this is the inventory of substrate the
Setup layer binds to:

- **Secrets denylist** (`src/schema/classify.ts`): applied at export time.
  `filterForYaml()` already knows what to drop.
- **YAML codec** (`src/schema/yaml.ts`): Setup manifest uses the same
  library; canonicalization is an additional pass.
- **Non-destructive merge** (`src/schema/yaml.ts#mergeYamlIntoLua`):
  `additive` apply mode is exactly this function.
- **Safe-write** (`src/fs/safeWrite.ts`): every import ends in a
  safe-write of `settings.reader.lua`.
- **Safety snapshot** (`src/commands/restore.ts` flow): pre-apply
  snapshot into `.kindly/pre-restore/<iso>.tar.gz`. Rollback = extract.
- **Archive primitives** (`src/fs/archive.ts`): fat Setups use this for
  create/extract (zip is a separate tool; we'll shell out to `zip`/`unzip`
  for the same reason we shell out to `tar`).
- **Diff engine** (`src/schema/diff.ts`): powers the "this will change X"
  preview before import applies.

```

    canonical.ts              # canonical YAML dump + sha256 over bytes
    hash.ts                   # content-hash helpers (lean + fat)

    unpack.ts                 # parse a .kset (lean or fat) into { manifest, files }

                              # subcommands: export, import, inspect, list, hash

tests/setup/
    schema.test.ts
    canonical.test.ts         # byte-stable YAML output; identical inputs → identical hashes
    pack.test.ts              # round-trip: pack → unpack → structurally identical

    import.test.ts            # integration: manifest → device w/ safety snapshot
```

## Build order

Each step is independently testable; each step below assumes the ones
above work.

1. **Manifest schema + validator.** TS types for `Setup v1`. Runtime
   validator (Zod or hand-rolled — decide at write time). Unit tests:
   valid manifests pass, malformed manifests fail with specific errors.
2. **Canonical YAML + content hash.** Dump a manifest with sorted keys
   and stable formatting. SHA-256 over bytes. Property-based test:
   reordering input keys produces identical canonical output.
3. **Lean export.** `kindly setup export <name>` reads device, filters
   secrets, writes lean manifest. Tests against fake Kindle.
4. **Inspect + list + hash.** Read-only subcommands. Tests.
5. **Lean import (additive).** Parse manifest, run diff engine for
   preview, take safety snapshot, merge + safe-write. Integration test:
   export → mutate device → import → device matches export.
6. **Replace apply-mode.** Same flow, but wipe non-declared keys first
   (keeping secrets/ephemerals as always-preserved classes). Test:
   declaring `apply_mode: replace` removes a key absent from the Setup.
7. **Fat setup pack/unpack.** Zip wrapper around manifest + plugins/ +
   patches/. Round-trip tests.
8. **Fat import with `--accept-plugins` / `--accept-patches`.** Install
   plugin dirs and patch files under `<koreader>/plugins/` and
   `<koreader>/patches/`. Refuse without the flags (with a message that
   spells out what the Setup contains, not a scolding).
9. **Compat metadata storage.** Read/write `compat` block. Enforcement
   deferred to v0.4.
10. **Templates.** Registry + `--template` flag on export. 3–5 curated
    templates to start: `minimal-ui`, `night-reading`, `distraction-free`.
11. **Dispatcher wiring** in `src/cli.ts`; top-level help updated.
12. **README + this doc updates.**

(v0.5 adds `import <url>`; v0.4 adds compat enforcement. Both are
separate build orders.)

## Resolved decisions

1. **Validator library:** **Zod.** Runtime-checked, great error messages,
   one small dep on top of `yaml`. Worth it.
2. **Archive format for fat Setups:** **tar.gz with extension `.kset`**.
   Reuses `src/fs/archive.ts` entirely — one codepath that already works
   on macOS, Linux, Windows 10+, and the Kindle itself. No new dep. Byte
   reproducibility doesn't matter at the archive level because the
   Setup's identity lives in the manifest (content-hash of canonical
   YAML, with embedded file hashes declared inside it) — the archive is
   pure transport.
3. **`kindly.yaml` vs Setup manifest:** **Kept separate.** `kindly.yaml`
   is a personal working copy (full-ish dump, user-editable). A Setup
   manifest is a curated, metadata-rich, shareable artifact with a
   versioned schema. They solve different problems; conflating them
   muddies both.

## Still open before coding

1. **Canonical YAML formatter.** The `yaml` package has sort options but
   not a full canonical mode. Plan: dump → parse → sort keys recursively
   → re-emit, then snapshot-test byte stability. Acceptable as long as
   two identical manifests produce identical bytes.
2. **Template format.** Are templates pre-filled Setup manifests bundled
   in the binary, or a higher-level DSL? Start with manifests (lowest
   complexity); add a DSL only if templates end up needing parameters.

## Notes / philosophy to preserve

- **The Setup manifest is the product's data contract.** Every future
  surface (frontend, remote distribution, template catalog, signing,
  cross-device) binds to `v1` or bumps to `v2`. Breaking changes are
  expensive. Lean on required-fields-minimal, optional-fields-generous.
- **Every risky import is a disclosure, not a block.** Copy must tell
  the user precisely what's in the Setup and what will execute, then
  let them proceed. The frontend's job (v0.7) is to make that
  disclosure legible; the CLI's job is to make the same facts available
  via `kindly setup inspect` before import.
- **Content hash is trust machinery.** "I pinned `kindly_setup_a1b2c3`
  on 2026-04-21; this import still shows hash a1b2c3, so nothing was
  tampered with" is a meaningful user-level guarantee. Preserve it.
