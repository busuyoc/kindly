# 70 — v0.5 — KOReader settings schema

v0.3 + v0.4 trust whatever keys the user or a manifest hand them. A typo
like `nightmode` (real bug from 2026-04-22 hardware testing: the user
wrote that instead of `night_mode`, kindly wrote it verbatim, KOReader
silently ignored it) round-trips clean through every validation we had.
v0.5 adds a schema layer that knows about the real KOReader settings
vocabulary and flags typos and type mismatches before they land on
device.

## Goal

Catch setting-key typos and type mismatches at the import/export
boundary, where they are cheap to fix. Do not pretend the schema is
complete or authoritative for all KOReader versions; ship a v1 extracted
from a live install, treat the schema file as data that can be
regenerated.

## Scope decisions

| # | Question | Decision |
|---|----------|----------|
| C1 | Source of truth? | **Extract from the KOReader source tree** (all `G_reader_settings:*("KEY")` calls in `frontend/` + `plugins/`). Augment with types observed in a live `settings.reader.lua`. One-shot script, re-runnable per KOReader release. |
| C2 | Type inference evidence order? | **method cluster > literal arg > observed value**. Boolean method cluster (`isTrue`/`nilOrFalse`/`flipNilOrTrue`/etc.) is unambiguous. `saveSetting/readSetting` with a Lua literal 2nd arg gives a literal type. The user's real settings file gives observed types for keys with no literal evidence. |
| C3 | What if evidence conflicts? | Mark `type: "unknown"` rather than lie. Validator treats `unknown` as "key exists, can't judge type" — never a mismatch. |
| C4 | Enforcement level? | **Warn by default, fail under `--strict`, silence unknowns under `--allow-unknown-keys`**. Covers the two legit reasons for an unknown key: typo (want warning) and plugin-scoped (want silence). |
| C5 | Where to run it? | `setup export` (validates the exported subset) and `setup import` (validates the incoming manifest). Not `pull`/`snapshot`/`restore` — those flow is "copy whatever the device has", warning the user about their own device's state is noise. |
| C6 | Nested-table keys? | **Top-level only in v1.** `footer` is validated as `type: table`; `footer.align` is not walked. The schema extractor doesn't expand table writes, so the inner structure isn't known. Nested coverage is a later concern. |

## Non-goals for v0.5

- Enum validation (`reader_footer_mode` must be in a specific set). Would
  need either source-annotation or hand-curation; deferred.
- Range validation. KOReader routinely introduces values outside old
  bounds; too brittle.
- Schema-per-KOReader-version diffing. The schema is tagged with the
  extraction's `git-rev`, but only one schema file ships. Re-extracting
  from a newer version replaces the old one.
- Did-you-mean suggestions ("did you mean `night_mode`?"). Nice to have
  later; not essential once the warning names the unknown key clearly.
- Plugin defaults schema, `docsettings` (.sdr) schema.

## Commands

No new commands. Behavior change on:

```
kindly setup export <name> [--strict] [--allow-unknown-keys] ...
kindly setup import <file>  [--strict] [--allow-unknown-keys] ...
```

Flag semantics:

- Default: warn on stderr per unknown key and per type mismatch; exit 0.
- `--strict`: any warning becomes a blocking error; exit 1.
- `--allow-unknown-keys`: suppress the unknown-key warnings (type
  mismatches still warn). Composes with `--strict`: strict still blocks
  on type mismatches but not on unknowns.

## Build order

1. `scripts/extract-schema.ts` — walk KOReader source, parse
   `G_reader_settings:METHOD("KEY"[, ARG])` calls, aggregate per key,
   infer type from method cluster + literal args.
2. Run against `/Volumes/Kindle/koreader`, commit
   `data/schemas/settings.reader.lua.v1.json`.
3. Augment with observed types from the live
   `settings.reader.lua` (same script, reads the device settings file
   by default when present).
4. `src/schema/settings.ts` — `loadSchema` + `validateKey`.
5. `src/schema/report.ts` — `validateSettings` + `formatValidationReport`.
6. Wire into `runSetupExport` with `--strict` / `--allow-unknown-keys`.
7. Wire into `runSetupImport` with same flags.
8. Docs + README.

## Notes / gotchas

- **The schema is data, not dogma.** It reflects one snapshot of KOReader
  source. Re-extract when KOReader releases add keys we haven't seen.
- **Unknown-key warnings on legitimate plugin keys are expected noise.**
  Users can silence per-run with `--allow-unknown-keys`; adding those
  keys to the schema is the long-term fix (with `source: "observed"`
  they show up as long as one user of that plugin runs the extractor).
- **Type "unknown" in schema ≠ key missing from schema.** `unknown` means
  "we know this key exists, we just don't know the type" — e.g. keys
  read from variables. Those never produce type-mismatch warnings.
- **Typos pass when `--allow-unknown-keys` is set.** This is a *feature*:
  the flag is for users who know their manifest has plugin-scoped keys
  the schema hasn't caught up with. A plain typo without the flag still
  warns — which is what we want.
- **Nested-table keys are opaque in v1.** `footer.align = "left"` inside
  a valid `footer` table won't be validated. If that turns out to be the
  actual typo vector, we escalate to nested-aware validation.
