## 0. Context

### What we've built (v0.1-v0.5)

Commands: `pull`, `apply`, `diff`, `init`, `doctor`, `snapshot`, `restore`,
`rollback`, `setup` (export/import/inspect/templates).

- **Engine**: byte-exact `settings.reader.lua` round-trip, atomic safe-write
  with .old rotation + post-write re-parse, per-key secret denylist,
  ephemeral filtering.
- **Snapshot/restore**: whole-tree tar.gz of plugins/patches/history.
- **Setups**: lean (`.kset.yaml`) + fat (`.kset` tar.gz) shareable manifests,
  `additive` + `replace` modes, 3 bundled templates, compat metadata
  (KOReader version window + device family) enforced at import with
  `--force` override.
- **Schema layer (v0.5)**: 557-key schema extracted from KOReader source
  + live observations, validates `setup export`/`import`, `--strict` + 
  `--allow-unknown-keys` flags.
- **Safety net**: 4 timestamp-keyed archive dirs (`backups`, `pre-import`,
  `pre-restore`, `pre-rollback`), plus `kindly rollback` for per-import
  revert.

546 tests green. Kindle-only, solo.

### Vision (from 2026-04-22, distilled)

A GUI for configuring KOReader's **built-in surfaces**:

- status bar, menu bar, plugin management, fonts, progress bar,
  screensavers, gestures — the always-shipped parts that don't churn
- Ninite/TuxMate-style bulk toggle for the ~40 default plugins (debloat
  preset is the hero flow)
- Upload someone's `.kset`, see rich preview BEFORE applying: what changes
  per category, which plugins in/out, visual diff where possible, books
  (later, via tar)
- Git-like feel over mutations: history, labels, diff per snapshot,
  `rollback --to N`
- Later: visual mockup or real-KOReader-on-desktop so toggles show
  instant feedback
- Later still: security scanning for suspicious Setups/plugins

Explicitly **not** in scope:

- SimpleUI-style typed schemas for third-party plugins (refused — marathon)
- Multi-device validation with strangers (paused; Claudiu has only a
  Kindle and doesn't want Android)
- Gist/GitHub-URL share (no strangers yet)
- Cloud/daemon/telemetry (never-build per 00-vision)

### Guiding principle

> *"If we do a good job on our configurations of the built-ins, we can
> emulate pretty advanced options of those fancy visual plugins."* — steel
> the foundation on what KOReader ships, then fancy plugins become a
> layer on top. We are not chasing SimpleUI's release cadence.

## 1. Four-lens brainstorm — Round 1

Each lens proposes independent work items from the vision. Unfiltered.

### 1.1 Technical lens

Focus: stable contracts, clean boundaries, file-format stability, GUI-ready
plumbing.

| # | Item | Rationale |
|---|------|-----------|
| T1 | **`--json` flag on every command** returning a typed result object, not stderr scraping. | GUI contract prerequisite. Today every consumer would regex stderr. |
| T2 | **Typed result shapes** in `src/types/results.ts` — `PullResult`, `ApplyResult`, `DiffResult`, `InspectResult`, `DoctorResult`, `HistoryResult`. Commands construct and return these; the CLI printer is a separate concern. | Locks a shape we can test against. Prevents "what does diff return?" archaeology when the GUI wires up. |
| T3 | **Semantic taxonomy** — `data/taxonomy/settings.v1.json`. Each known key → `{category, label, description, control_hint}`. Ships as regeneratable data, just like the schema. | The category tree is what the GUI sidebar renders. Without it, GUI has to hardcode its own. |
| T4 | **Library extraction** — carve pure functions out of `src/commands/*.ts` into `src/lib/` (`pull()`, `apply()`, `diff()`, `importSetup()`, etc.). CLI becomes presentation. | GUI can `import { pull } from 'kindly/lib'` without shelling out. Boundary clarity. |
| T5 | **History index** — append-only `.kindly/history.jsonl`. One line per mutation with `{timestamp, command, label?, summary, backup_path, pre_import_path?}`. | Snapshots already exist as folders with stamps — unqueryable. History index makes "show me my last 20 changes" a single read. |
| T6 | **Structured diff** grouped by taxonomy — `{"fonts": [{key, before, after}], "status_bar": [...]}`. | `kindly diff --json` and `setup inspect --json` become the preview API. |
| T7 | **Plugin catalog** — `data/catalog/plugins.bundled.v1.json`. ~40 default KOReader plugins: `{name, folder, description, ship_default_on, category, curation_opinion}`. | The Ninite render target. Without this, no "check what you want" list exists. |
| T8 | **`kindly serve` long-running JSON-IPC mode** over stdin/stdout. GUI spawns it once, streams commands instead of spawning per invocation. | Startup cost matters when GUI is polling. ~50ms × N commands adds up. |
| T9 | **Output versioning** — every JSON output has `$schema_version`, `generated_at`, `kindly_version`. | GUI compiled against v0.6 JSON should know when it hits v0.8 JSON that shapes may differ. |
| T10 | **`kindly trace` (opt-in)** — `.kindly/trace.jsonl` with invocation + duration + outcome. Self-dogfood surface. | Claudiu is his own test user. Quantify his own friction. |

### 1.2 Product lens

| # | Item | Rationale |
|---|------|-----------|
| P1 | **Preview-first import** — `kindly setup import` shows structured preview + waits for confirmation by default. `--yes` (or non-TTY stdin) skips. | Today `--dry-run` is opt-in. Flip the polarity: safety first, speed via flag. |
| P2 | **Named snapshots** — `--label "before-experiment"` on `snapshot`, `apply`, `setup import`. Label persists in history. | Users remember names, not ISO stamps. |
| P3 | **`kindly history`** — human-readable log of mutations with labels. | The git-log equivalent of "what did I do." |
| P4 | **Rich diff** — group by taxonomy, expandable. `Fonts: 2 changes / Status bar: 1 change / Plugins: +2 -1`. With human-impact hints on numeric keys (`font_size 18→22 = +22% larger text`). | Raw keys are developer-friendly, not user-friendly. |
| P5 | **`kindly plugin describe <name>`** — catalog read. Shows what it does + current state + default state + curation opinion. | GUI tooltip source. Also usable standalone. |
| P6 | **Structured error remediation** — every error result carries `{code, message, remediation[]}` where each remediation is `{text, command?}`. GUI renders as a button; CLI renders as a line. | "Device not mounted — try: `kindly doctor`" is more helpful than "ENOENT". |
| P7 | **Template preview** — `kindly setup templates --show night-reading` shows what would change on THIS device, not abstractly. | Today `templates` lists names. Useful, but the next question is always "what does it do to me?" |
| P8 | **Interactive apply** — `kindly apply` (no `--dry-run`) shows diff, asks to confirm on TTY. `--yes` to skip. | Pair of P1 for the pull/apply loop. |
| P9 | **Debloat preset as first-class template** — `kindly setup templates --show debloat` uses the catalog's curation_opinion. | The Ninite hero flow. |

## 2. Cross-critique — Round 2

Each lens attacks the other three's items. Tensions surface here; resolutions
get logged.

### Technical ↘ Product

- **P1/P8 (preview-first default)** will break CI scripts that do
  `kindly setup import foo.kset` silently. Tech position: acceptable
  only if TTY-gated — piped stdin or `CI=1` env → silent; TTY → preview.
  Resolution: **accept, gate on TTY**. Tests must assert both modes.
- **P6 (structured remediation)** sounds simple but requires introducing
  a result-object pattern (today everything throws `Error`). Tech
  resolution: introduce `KindlyError extends Error` with `{code, remediation[]}`;
  existing `ArgError` / `LuaParseError` extend it. Not a rewrite — a type
  refinement.

### Technical ↘ UX-Research

- **UX4 (mockup library)** — licensing risk if we ship KOReader's own
  UI screenshots. Resolution: **only screenshots of Claudiu's own
  device**, documented as such, or hand-drawn mockups. Never copy
  upstream assets.
- **UX5 (GUI framework decision)** — picking it now is premature if
  we don't know the JSON surface fully. Reverse: the JSON surface
  IS defined by v0.6-v0.7. Decide UX5 at the start of v0.10, with
  the surface already finalized.

### Product ↘ Technical

- **T1 (`--json` flag everywhere)** — without versioning (T9), a GUI
  compiled at v0.6 breaks silently at v0.8 if we rename a field.
  Resolution: **T1 and T9 ship together**, never T1 alone.
- **T2 (typed results)** — if we export from `src/lib/` a user could
  `import { PullResult }` from npm. That's an API commitment.
  Resolution: **keep extraction internal** to the repo; the future GUI
  is co-located; no npm publish for v0.6-v1.0.
- **T5 (history.jsonl)** — what happens at 10,000 mutations? Rotation
  policy? Resolution: cap at 500 entries; rotate to
  `.kindly/history-archive/YYYY-MM.jsonl`. Add to spec.
- **T8 (`kindly serve`)** — premature. Per-invocation spawn is ~80ms
  on Bun; at 10 commands/second it's not a bottleneck. Defer to v0.10.

### Product ↘ UX-Research

- **UX1 (weekly dogfooding)** — without structured logging, "note 3
  frictions" is lossy memory work. Hook into T10 trace. Resolution:
  weekly cadence, trace + freeform notes in `.claude/dogfooding/YYYY-WW.md`.
- **UX3 (plugin curation)** — Claudiu's opinion ≠ KOReader's. If we
  surface only ours, users disagree and resent the tool. Resolution:
  **always show both**: `ship_default_on: true, curation_opinion: "debloat"`.
  GUI renders both; user picks.

### UX-Research ↘ Technical

- **T3 (taxonomy)** — if we mirror KOReader's menu structure, we
  inherit the cockpit problem we're trying to solve. Resolution:
  **flat taxonomy**, ~10 categories, optimized for a GUI sidebar,
  not for upstream menu fidelity.
- **T6 (structured diff)** — diffs that look small to developers look
  huge to users (e.g. any change to the status bar feels visually
  loud). Resolution: **diff includes a severity hint**: `trivial` /
  `visual` / `functional` / `breaking`. GUI renders with badges.

### UX-Research ↘ Product

- **P2 (labels)** — labels collide. "before-experiment" used twice
  overwrites? Resolution: labels are **advisory, not unique**; stamp
  is canonical. History can show "before-experiment (3 snapshots)".
- **P7 (template previews)** — tells the user what changes AGAINST
  their device, but what if the template is meant for a *fresh* device?
  Some templates should show "changes from default" instead.
  Resolution: **preview has two modes** — vs-device (default) and
  vs-default (flag).

### Business ↘ Technical

- **T7 (plugin catalog)** — curating 40 plugins = work. Source: KOReader
  `_meta.lua` (grep-based per 13-research §_meta.lua warning) + hand-edit.
  Budget: 1-2 days. Accepted.
- **T8 (`kindly serve`)** — as part of boundary design, not perf.
  Already deferred by Product's critique. Aligned.
- **T4 (library extraction)** — over 4 weeks of work if done thoroughly.
  Resolution: **do it in two slabs**: v0.6 exposes pure functions for the
  5 core commands (pull/apply/diff/inspect/doctor). The rest come when
  GUI needs them. Not upfront.

### Business ↘ Product

- **P1 (preview-first)** — adds time-to-apply for power users.
  TTY-gating (Tech's fix) resolves. Accepted.
- **P9 (debloat template)** — good, but naming matters. "Debloat" is
  aggressive; KOReader ships 40 on purpose. Consider `minimal-bundled`
  or similar. Revisit at v0.9 authoring.

### Business ↘ UX-Research

- **UX5 (GUI framework)** — Tauri wins on bundle size + security
  sandbox model; loses on Claudiu's day-to-day TS ergonomics (Rust
  shell). Bun + webview (`Bun.serve` + system webview) is emerging but
  less mature. Electron is heaviest but most battle-tested. **Record
  the decision at v0.10 kickoff** with concrete benchmark data
  (startup time, bundle size on macOS/Windows/Linux).

## 3. Unified build order — Round 3

Six phases, v0.6 → v1.0. Each phase is shippable alone (tagged release,
CHANGELOG entry). Cross-check table at §5 maps every R1 item to a phase.

### v0.6 — Structured I/O foundation (2-3 weeks)

**Goal:** every command speaks JSON. GUI contract locked.

| W# | Work item | DoD |
|----|-----------|-----|
| W1 | Typed result types in `src/types/results.ts` | Every command function returns a typed object before printing. Existing text output is driven from the result. Tests assert result shape per command. |
| W2 | `KindlyError extends Error` with `{code, remediation[]}`; `ArgError`, `LuaParseError` migrated | Every throw has a `code`. CLI renderer maps `remediation[]` to text lines. Tests cover code + remediation roundtrip. |
| W3 | `--json` flag on `pull`, `apply`, `diff`, `doctor`, `snapshot`, `restore`, `rollback`, `setup inspect`, `setup import --dry-run`, `setup export --dry-run` | `--json` outputs a single JSON object conforming to the typed shape, no stderr noise (warnings become a `warnings[]` array in the JSON). Tests: each command twice, text + json. |
| W4 | JSON envelope with `$schema_version`, `generated_at`, `kindly_version` | All `--json` outputs wrapped. `$schema_version` is 1 for v0.6. |
| W5 | `.kindly/trace.jsonl` — opt-in via `KINDLY_TRACE=1` env. One line per invocation: `{ts, cmd, argv_hash, duration_ms, exit_code, warnings_n}`. | Trace file is append-only; rotation at 10MB → archive. Secret-free (hash of argv, not argv). |
| W6 | Docs: `docs/82-json-api.md` — the JSON output contract per command | Lives in repo. GUI reads this as its spec. |

**Risks:**
- R6.1: JSON migration regressions — mitigated by dual-asserting text+json in the existing test suite. New tests per command.
- R6.2: `--json` + interactive TTY modes interact (e.g. P1 preview-first). Decision: `--json` implies non-interactive. Force `--yes` or non-TTY.

| W# | Work item | DoD |

## 7. Guardrails (don't regress)

Every phase must hold:

- **546 tests stay green** (count goes up, not down).
- **Byte-exact round-trip** on the 180-key fixture. Non-negotiable — this is
  the product.
- **No new mutation path** bypasses the safe-write pipeline or history index
  (once v0.8 ships).
- **No TTY-dependent code in `runX`** — commands return results, the CLI
  layer decides to prompt or not based on env.
- **No telemetry**, not even anonymous. Ever. Reaffirmed in CONTRIBUTING.
- **Schema/taxonomy/catalog stay regeneratable from source.** No hand-edited
  files that can't be reproduced from KOReader checkout + a script.
- **Secrets denylist still enforced** at every new boundary (history, IPC,
  catalog, serve).

## Lens lessons — framework-level (suggested, not applied)

New principles worth considering for the lens files:

### Suggested for `planner-brain.md`

**"A paused validation lens doesn't become mute — it morphs into self-dogfooding + competitor audit + asset curation."**
> When user validation is explicitly unavailable, UX-R still produces
> value via JTBD on the founder + prior-art analysis + visual asset
> collection. Killing the lens is worse than redirecting it.

### Suggested for `planner-lens-technical.md`

**"Data assets are the moat for tools that wrap an existing OSS project."**
> When building tooling around a project you don't control (kindly →
> KOReader), the schema, taxonomy, and catalog you curate are what
> makes your tool not trivially forkable. Invest in data as seriously
> as in code. Track the assets in the same way you track services.

### Suggested for `planner-lens-product.md`

**"Preview-first should be the default; speed is a flag."**
> For any mutation against user state, the default should be preview +
> confirm; `--yes` is the opt-in to silent. Reverses the usual CLI
> convention (`--dry-run` opt-in) in favor of safety. TTY-gating
> solves the CI scripting concern.
