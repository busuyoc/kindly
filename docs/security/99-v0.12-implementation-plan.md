# 99 — v0.12 Implementation Plan

> **Snapshot.** This plan reflects red-team findings accumulated through
> 2026-04-24: ~114 findings across 37 angles (documented in `96a`/`96b`/`96c`
> and angle-memory files under `~/.claude/memory/project_kindly_redteam_*`).
> It is **not exhaustive**. §6 enumerates known-open angles; anything not
> listed there is an unknown unknown. Re-run the audit when any of the
> following change: (a) distribution model moves T2 → T3, (b) a cryptographic
> boundary is introduced (W39 signing), (c) trusted upstream (KOReader minor
> bump), (d) runtime (Bun major bump, Node fallback added), (e) device
> family expands beyond Kindle.
>
> Date stamps on each cluster show last empirical probe. Anything older than
> the current minor release is due for re-probe.

> **Scope freeze policy (hard rule).** Findings discovered *after* this plan
> was drafted queue into **v0.13 by default**. They enter v0.12 mid-flight
> only if ALL of the following hold:
>
> 1. **P0 severity** — active exploit primitive or trivially reproducible RCE /
>    data-loss.
> 2. **Affects T1 users today** — not just T2-amplified; a single-user Kindle
>    owner is exposed without opting into anything.
> 3. **No user-side workaround** — can't be mitigated by "don't use feature X"
>    or "wait for patch."
> 4. **Would re-open a finding that v0.12 claims to close** — i.e., a
>    regression on the closed set, not a new angle.
>
> All four must hold. HIGH severity alone does not qualify. The critical path
> (§3) has a fixed surface area the day v0.12 branches; every mid-flight
> addition slips the ship date and cascades into §3's decision gates. This
> policy exists because v0.11 proved that probing the code finds more HIGHs
> than implementation closes — an infinite regress is the default state, and
> a line has to be drawn somewhere.
>
> Everything else, regardless of severity label, goes to v0.13's §6-equivalent.
> Running tally lives in `~/.claude/memory/project_kindly_redteam_triage.md`.

**Two shipping modes determine the work:**

- **T1 — single-user CLI on own Kindle.** Attacker is the user themselves
  or any malware they've already caught. Many findings degrade to "shoot
  yourself in the foot" severity.
- **T2 — community distribution (strangers ship `.kset`).** Attacker is
  the `.kset` publisher. Every byte in a manifest is adversarial until
  gated. This is where the real cryptographic work lives.
- **T3 — server-hosted (multi-tenant).** Deferred. Separate scope, separate
  sprint.

A finding's severity under T1 is often much lower than under T2. Where
relevant each cluster lists the tag.

### Q1 — What does the signature cover? **[DECIDED 2026-04-24: canonical extracted tree]**

| Option | Pro | Con |
|---|---|---|
| Raw `.kset` bytes | Trivial to implement; no canonicalization dependency | Fragile: yaml-lib bump / pretty-printer diff / tar framing (sparse vs dense, S1452) invalidates every sig |
| Canonical extracted tree (post-unpack hash) | Robust to container repackaging; S1452/S1453 become structurally impossible | Unpack must precede verify (inverts safe order); canonical.ts becomes trust root |
| Canonical bytes (yaml re-emit) | Robust to quoting diffs | Trust root = canonical + yaml emitter; any bug = forgery primitive |

**Recommendation: canonical extracted tree.** Two reasons that dominate.
First, S1452 (sparse tar bomb 150,000:1) and S1453 (zip-as-`.kset` bypass)
become **structurally impossible** — if identity is over the extracted
content, tar framing drift and container polyglots cannot affect the hash.
The alternative (raw-bytes) means every container attack has to be closed
defensively in C4, forever, against every new archive format. Second,
W46's reproducibility goal is easier to hit when different builders can
produce different-but-equivalent containers — pinning tar invocation
across platforms (sparse flags, PAX headers, file order) to get byte-exact
is fragile; pinning the canonical function is already a requirement
whichever canonical option you pick. The "unpack before verify" concern
is addressed by keeping C4 archive caps + magic-byte sniff *before* hash
computation, so a malicious container can't make us OOM in the unpacker.

### Q2 — Classify filter semantics? **[DECIDED 2026-04-24: Option B — verifier-independent re-filter]**

The filter (C1) strips control bytes, NFC-normalizes, removes disallowed
keys. The question is **where it runs** and **what the verifier does with
its output**.

- **Option A — Publisher-side transform.** Publisher's build pipeline
  runs the filter, ships the filtered bytes, signs them. Verifier checks
  the sig and applies the bytes as-is. What the verifier implicitly
  trusts: "the publisher's filter ran, and it ran correctly."
- **Option B — Verifier-independent re-filter.** Publisher ships whatever
  they want. Verifier re-runs the filter, then checks whether `filter
  (input) == input`. If not equal, the verifier **rejects the entire
  `.kset`** — refuses to apply, refuses to trust the sig, marks the
  package malformed. What the verifier implicitly trusts: nothing about
  the publisher's filter. The filter is the verifier's own membership
  test on the set of acceptable bytes.

| Option | Pro | Con |
|---|---|---|
| A — Publisher-side transform | Simple; publisher-side only; verifier just sig-checks | Sig covers whatever the publisher shipped. Compromised CI / negligent author / forked legacy tooling = signed malicious `.kset` that passes verify |
| B — Verifier-independent re-filter | Defends against compromised publisher pipelines; sig proves publisher-identity, re-filter proves bytes are in accepted shape | Any publisher-side drift (yaml emitter whitespace, NFC output ≠ input) fails verify even on honest publishers |

**Recommendation: Option B — verifier-independent re-filter.** What gets
rejected is explicitly: **any `.kset` whose bytes are not already filter-
invariant on the verifier side**. The publisher's sig proves who built
the package; re-filtering proves the bytes are in acceptable shape.
Trusting the sig alone is what Option A does, and it means a compromised
publisher pipeline silently produces authentic-looking malicious packages.

The cited downside — "publisher-side non-determinism breaks verify on
honest publishers" — is actually the feature. Drift surfaces in the
publisher's own CI (they run the same re-filter test locally before
shipping), forcing them to fix pipeline non-determinism before any user
sees a broken `.kset`. Sheriff at the gate beats trust-by-assertion.
Couples cleanly with Q1=canonical-tree: the re-filter operates on post-
canonical output, so canonical drift and filter drift are one combined
test.

### Q2a — Filter version coupling **[DECIDED 2026-04-24: `filter_version` field, N=2 generation window]**

Option B makes the filter itself part of the implicit signed contract: a
`.kset` signed under v0.12's filter rules must remain filter-invariant
under v0.12's filter. When v0.13 tightens the filter (new Unicode class,
new control-byte rule, additional classify entry), a `.kset` that was
filter-invariant under v0.12 **may stop being invariant** under v0.13 —
sig is still valid, bytes haven't changed, but the verifier's re-filter
produces different output and rejects.

This is an ecosystem question, not a mechanical one. Three options:

| Option | Pro | Con |
|---|---|---|
| `filter_version` field in `.kset` meta; kindly keeps N=2 generations (current + current-1) and rejects older explicitly with a clear error | Honest publishers get a grace window (one release cycle); bounded trust-code surface; old filter bugs expire on a schedule | kindly carries 2 filter generations each release; adds small code complexity per release |
| `filter_version` field; all historical versions kept forever | Every historical `.kset` verifies indefinitely; strongest ecosystem continuity | Trust-code surface grows unboundedly; yesterday's filter bugs become permanent compat contracts |
| No version field; filter changes are declared ecosystem-breaking (re-sign everything) | Simplest implementation; forces alignment on "what's acceptable" | High churn; breaks Ninite-style curated catalogs at every release; publishers abandon packages |

**Recommendation: `filter_version` field with N=2 generation policy.** The
grace window is usually sufficient for active publishers; abandoned
packages fail loudly with an explicit error (not silent breakage);
trust-code surface stays bounded. Critically: the rejection message tells
the user *why* ("signed for filter v1, verifier is v3") instead of the
confusing "filter-invariant check failed" they'd see today. Couples with
the `.kset` manifest having a versioned `meta.kindly_filter` block, not
just the overall `kindly_setup: v1` schema version.

**Implementation note:** the filter version is independent of the manifest
schema version. A schema evolution (new optional field) should not bump
filter version; a filter behavior change (new disallowed codepoint) must.

### Q2b — Publisher tooling: make un-prepared bytes unsignable **[DECIDED 2026-04-24: mandatory `prepare` step, `sign` refuses unprepared input]**

Without operational tooling, publishers will inevitably: hand-author
`.kset`, sign without running the filter, ship, get rejected by the first
consumer, and blame kindly. The failure mode is predictable enough to
design against.

| Option | Pro | Con |
|---|---|---|
| `kindly setup prepare <file>` mandatory; `kindly setup sign` refuses input that isn't prepare's output | Impossible to sign un-prepared bytes; workflow enforces itself | Adds a required step publishers could try to work around |
| Docs warn publishers to run the filter before signing | Zero tooling complexity | Guaranteed someone forgets; ecosystem fills with broken sigs; kindly gets blamed |
| `kindly setup sign` internally runs prepare and signs the prepared output, no separate step | One-command UX; un-prepared bytes can't leave the publisher's machine | Hides what prepare does; publisher who runs prepare's logic separately (CI, external tooling) gets confusing double-filter behavior |

**Recommendation: mandatory `prepare` as a distinct step, with `sign`
refusing unprepared input.** The friction is the feature — separating
prepare and sign makes the filter behavior explicit and auditable. The
flow:

1. `kindly setup prepare manifest.yaml` — runs the filter, reports whether
   bytes were already invariant. If not, emits the filtered output
   alongside a diff so the publisher sees exactly what changed. Stamps
   `meta.kindly_filter.prepared_hash: sha256(filter_applied_content)` into
   the output.
2. `kindly setup sign prepared.kset --key <...>` — refuses to sign if the
   `prepared_hash` field is absent or doesn't match actual content.
3. Verifier side: re-runs filter, checks `filter(input) == input`, checks
   `prepared_hash` matches, checks sig. All four gates.

This makes it structurally impossible to sign bytes that haven't been
filtered. Publishers who run external filtering tools still invoke
`prepare` as the canonical last step — `prepare` on already-filtered input
is a no-op, just stamps the hash.

### Q3 — W46 rebuild contract? **[DECIDED 2026-04-24: canonical-hash-identical]**

| Option | Pro | Con |
|---|---|---|
| Bytewise-identical rebuild | Strongest assurance; auditor can check a hash | Requires pinning every input: Bun, yaml, tar, locale, filesystem ordering — fragile supply |
| Canonical-hash-identical rebuild | Decouples container from identity; Docker can use any tar | Only meaningful if Q1 picks canonical identity |

**Recommendation: canonical-hash-identical.** Bytewise pinning is a
supply-chain nightmare — every one of {Bun version, yaml emitter version,
tar invocation, LC_ALL, filesystem ordering, macOS NFD vs Linux NFC} is a
trust-root dependency. One drift and rebuild fails for everyone.
Canonical-hash-identical only adds the canonical function itself to the
trust root, which Q1=canonical-tree already requires. Third-party
auditors can rebuild with any reasonable toolchain, compute canonical
hash, compare. This matches how language-level build reproducibility
projects (Debian reproducible-builds, Rust's `cargo-vet`) converged —
bytewise was abandoned for equivalent-output-under-canonical everywhere
the containers are allowed to vary.

## 4. Architectural-not-patch items

These look like one-line fixes but aren't — each needs a product call.

- **GUI auto-apply avoidance.** `kindly serve` + GUI can trivially trigger
  concurrent applies (double-click, watch+apply race, retry-on-transient
  loops). S980–S984 are **v1.0 GUI blockers**. The CLI today is "safe" only
  because humans type one command at a time. C3 lockfile is necessary but
  not sufficient — the GUI needs a state machine that refuses to queue a
  second apply while one is in flight.
- **SDL emulator boundary.** Per Angle S: the pixel-accurate preview in
  the v1.0 GUI vision requires running KOReader in SDL. Today kindly does
  not invoke KOReader; the moment it does, the trust boundary moves. Needs
  a full threat-model re-triage under "we now execute upstream Lua."
- **Signed `.kset` vs built-ins-only.** If T2 community distribution is
  permanently built-ins-only (the "Ninite for KOReader" vision), W39
  signing might not be strictly required — the attack surface is much
  smaller. If user-authored `.kset` is ever supported, W39 is mandatory.
  This is a product scope decision, not a technical one.
- **Concurrent mount semantics.** Two Kindles at `/Volumes/Kindle` — macOS
  appends `/Volumes/Kindle 1`. Does `kindly` resolve the first match
  silently (today) or require explicit disambiguation? S1390 argues the
  latter.
- **KOReader upstream bug reports.** S1100/S1101 are KOReader bugs, not
  kindly bugs. kindly mitigates by filtering; KOReader should also `util.
  shell_escape` those sites. File upstream.

## 8. Open questions needing author decision

These block the critical path. Each has a recommended call with the
reasoning; author can override.

1. **Q1** (§2) — Identity: raw bytes / canonical tree / canonical bytes?
   → **Canonical tree.** Structurally closes S1452/S1453; decouples
   container from identity for W46.
2. **Q2** (§2) — Filter trust model: publisher-side transform (A) or
   verifier-independent re-filter (B)?
   → **Option B.** Verifier re-runs the filter and rejects any `.kset`
   whose bytes are not already filter-invariant. The sig proves
   publisher-identity; the re-filter proves the bytes are in accepted
   shape. Without B, a compromised publisher pipeline silently ships
   authentic-looking malicious packages that pass verify.
2a. **Q2a** (§2) — Filter version coupling: embed `filter_version`
    keep-N-generations / embed keep-forever / no field, ecosystem-break?
    → **`filter_version` field, N=2 generations.** Bounded trust-code
    surface; honest publishers get a one-release grace window; rejection
    messages tell users *why* instead of silent breakage.
2b. **Q2b** (§2) — Publisher tooling: mandatory `prepare`+`sign` /
    docs-only warning / `sign` auto-prepares?
    → **Mandatory `prepare` as distinct step; `sign` refuses unprepared
    input.** Makes un-filtered bytes unsignable at the tooling level;
    failure mode "publisher forgets to filter" becomes structurally
    impossible. `prepared_hash` field + verifier gate closes the loop.
3. **Q3** (§2) — Rebuild contract: bytewise or canonical-hash?
   → **Canonical-hash-identical.** Bytewise pins every element of the
   build toolchain forever; canonical-hash only pins the canonical
   function (already in trust root from Q1).
4. **Q4 — Scope** (§4) — T2 permanently built-ins-only, or user-authored
   `.kset` for v1.0?
   → **Built-ins-only for v1.0, user-authored unlocked in v2.0.**
   Distinct from infrastructure timing: the W39 signing primitive,
   `filter_version` carry-list, and key-distribution mechanism land in
   **v0.13** so v1.0 ships built-ins-only on top of finished plumbing
   (kindly-maintainer-signed catalog, single trust root). v2.0 then
   opens the floodgate to user-authored `.kset` by adding TOFU pin
   store, key-rotation UX, and revocation protocol on top — no
   substrate work needed at that point. This split avoids the v1.0
   slip that would come from coupling user-authored T2 to the
   v1.0 ship date.
5. **Q5 — Scope** (§4) — `kindly serve` owns mount exclusively, or shares?
   → **Exclusive ownership while serve is running.** Simpler state
   machine; eliminates half of C3's concurrency discipline inside the
   GUI flow; CLI-alongside-GUI becomes an explicit anti-pattern that
   serve refuses. Users who want CLI can stop the daemon — that's a one-
   sentence docs note, not a lock-protocol.
6. **Q6 — Scope** (§4) — SDL emulator in v1.0 scope, and when's the
   threat-model pass?
   → **Yes, in v1.0 scope; threat-model pass before any implementation
   starts.** The pixel-accurate preview is the vision differentiator per
   `project_kindly_gui_preview_vision`. But kindly starts executing
   upstream Lua the moment SDL lands — that's a trust-boundary move,
   needs a full angle-pass dedicated to it before code. Block C1/C7
   implementation from touching anything emulator-adjacent until that
   pass exists.

Override any of these and the plan's shape changes — §2 especially. Until
Q1–Q3 are called, the §2 critical path cannot start. Fix clusters in §3
are unblocked and can begin immediately.
