# W39 — Built-in publisher keyring

**Status:** ✔ DONE 2026-04-26 (v0.13)
**Spec source:** `docs/security/99-v0.12-implementation-plan.md` §2 layer 5,
§5 (signature algorithm row), §7 (closed-in-v0.13).
**Plan source:** `/Users/claw/.claude/plans/eventual-forging-creek.md`.

## 1. What this closes

W39 split into a **recipient half** (the local trust roster — closed
2026-04-26) and an **upstream half** (how publisher keys reach a fresh
install in the first place). This doc covers the upstream half.

The recipient half is `~/.kindly/trusted-keys.json` populated by the
user's own `kindly setup trust add <publisher.pub>`. That answers
"do I trust *this* signer?" once the user has the key in front of
them. It does *not* solve the **first-encounter problem**: how does
a fresh install know to trust the maintainer who signed the starter
Setup the user is about to import?

`src/setup/keyring.ts:13-17` is explicit that we will not TOFU the
answer ("the first encounter with an unknown signer is exactly when
impersonation is most likely to succeed"). The alternative this work
ships is a curated registry committed in source.

## 2. Mechanism

### 2.1 Data layout

`data/keyring/publishers.v1.json` — committed registry.

```json
{
  "kindly_builtin_keyring": "v1",
  "curated_at": "2026-04-26",
  "publishers": []
}
```

v0.13 ships the file with `publishers: []`. Curation lands in v1.0
alpha — the maintainer signs known starter Setups, lands the public
keys here, and tags v1.0.

Schema (`src/setup/builtinKeyring.ts`):

| Field | Required | Constraint |
|---|---|---|
| `key_id` | yes | `sha256:` + 64 lowercase hex (matches `keyring.ts:48`) |
| `public_key_b64` | yes | 44-char base64 of raw 32B Ed25519 (matches `keyring.ts:50`) |
| `label` | yes | 1–120 chars; user reads in `setup trust list` |
| `description` | no | up to 500 chars |
| `since` | no | release tag string ("v1.0.0") |
| `references` | no | up to 10 URLs; scheme allowlist `http(s)/mailto/git+https` (mirrors S961) |

`label` is **required** — no anonymous entries in the curated
registry. The user can read `setup trust list` and tell
`kindly-builtin: alice` apart from a randomly-named local key.

`added_at` (local) → `since` (built-in); semantics differ. Local
records *when the user added the key*; built-in records *which
release first shipped it*.

Zod `.strict()` on every object (closes Batch N S301 passthrough
hazard).

### 2.2 Hash binding

A SHA-256 of the JSON file's bytes is baked into source as a TS
constant (`src/setup/builtinKeyringHash.ts`). Auto-generated by
`scripts/build-builtin-keyring.ts`. CI invariant:

```
bun run scripts/build-builtin-keyring.ts && \
  git diff --exit-code src/setup/builtinKeyringHash.ts
```

Post-install tamper or packager swap mutates the JSON; `loadBuiltinKeyring`
fails closed with `BUILTIN_KEYRING_HASH_MISMATCH`. Closes Batch N S306.

### 2.3 Loader

`src/setup/builtinKeyring.ts` — discipline tightened relative to
`src/catalog/reader.ts`:

- Path: hard-resolved via `import.meta.dir + "../../data/keyring/..."`.
  No cwd-override hatch (closes Batch N S300).
- Size cap: 64 KiB before parse (closes S305). Stat-then-read short-
  circuits multi-MiB packager swaps.
- Hash check: `hashBytes(bytes) === BUILTIN_KEYRING_HASH` or hard-fail
  with remediation pointing at reinstall + `bun run scripts/...` for
  legitimate edits.
- Zod strict on envelope and publisher entries (closes S301).
- Display strings flow through the renderer's `sanitizeForTerminal`
  chokepoint at render time (Batch M); load returns raw validated
  bytes.

Cache: `loadBuiltinKeyring()` memoizes the validated result for the
process lifetime. The file is committed-in-source — it cannot
legitimately change while the process runs. Tests use
`_resetBuiltinKeyringCacheForTests()` and
`_overrideBuiltinKeyringForTests()` seams; production never calls
them.

### 2.4 Trust resolution

`src/gates/producers/signerTrust.ts` consults both rosters in this
order:

1. **Built-in keyring** loaded first. A `BUILTIN_KEYRING_HASH_MISMATCH`
   propagates as a hard `KindlyError` — a tampered install cannot be
   sidestepped via the user's personal trust list.
2. **Local roster** — if the signer is found locally, return
   `trustSource: "local"` with the user's chosen label.
3. **Built-in fallback** — if not local, look up in built-in;
   return `trustSource: "builtin"` with `label: "kindly-builtin: <name>"`.
4. Otherwise `rosterStatus: "untrusted"`.

Local wins when both rosters contain the same key. Audit clarity:
the user's explicit `trust add` is the source of record. The CLI
guard (§2.5) prevents creating new duplicate state, but precedence
handles the legitimate upgrade scenario where the local entry
predated the built-in.

The gate definition at `src/gates/definitions/identity.ts` does
**not** change — `rosterStatus` remains `trusted`/`untrusted`/
`roster-error`. Only the side-channel `trustSource` + decorated
`signerLabel` flow through to `setup verify --json`.

### 2.5 CLI surface

`setup verify --json` envelope adds:

```ts
{
  ...existing fields,
  trust_source?: "local" | "builtin"   // present iff trusted
}
```

Pretty output appends `(built-in)` after the label when `trust_source
=== "builtin"`.

`setup trust list`:

- Pretty: groups under "built-in (kindly-curated) — N" and "local — N"
  headers.
- `--json`: returns `{builtin: [...], local: [...]}`.

`setup trust add <pub>`: derives `key_id` from the public key and
checks the built-in registry **before** mutating the local roster.
On match, throws `BUILTIN_KEY_ALREADY_TRUSTED` with remediation
"this key is already trusted via the built-in registry; no local
entry needed."

`setup trust remove <id>`: prefix-matches the built-in roster first.
On match, throws `BUILTIN_KEY_NOT_REMOVABLE` with remediation "built-in
keys are managed by kindly upgrades; edit
data/keyring/publishers.v1.json and rebuild via
`bun run scripts/build-builtin-keyring.ts`."

No new top-level commands. `setup trust list` is the only UX a user
needs to see what they trust.

## 3. Threat model

### 3.1 Threat: curation trust

The curated set is whatever kindly maintainers commit to
`data/keyring/publishers.v1.json`. A user installing kindly is
implicitly trusting the maintainer team's curation judgment.

**Mitigation:** make the trust visible. `setup trust list` always
shows the built-in entries with their labels; the user sees exactly
who they trust by default. The `references[]` field on each entry
points at the publisher's public-key declarations (GitHub profile,
mailing-list announcement) so a curious user can cross-check.

**Not mitigated:** if the kindly maintainer team is compromised, the
curated set is compromised — this is the same trust assumption as
the npm package itself. Out of scope for v1.0; v2.0's TOFU pin store
gives users a way to override or pin specific keys independent of
the built-in set.

### 3.2 Threat: post-install file tamper

Attacker replaces `data/keyring/publishers.v1.json` after install
with their own publisher key, producing setups that verify-trusted.

**Mitigation:** `BUILTIN_KEYRING_HASH` constant baked in TS source.
Editing the JSON without regenerating the hash fails load with
`BUILTIN_KEYRING_HASH_MISMATCH`. Editing the hash constant requires
modifying `.ts` source — at which point the attacker has package-
write access and can compromise anything.

**Not mitigated:** an attacker with full write access to the
installed bundle (both JSON + TS source). This is equivalent to
arbitrary code execution against the install — the keyring is not
the weakest link.

### 3.3 Threat: packager-supply-chain swap

A package-distribution intermediary (npm registry compromise, CDN
poisoning) swaps the JSON file with a multi-MiB malicious version.

**Mitigation:** 64 KiB size cap before parse. A packager swap with
a multi-MiB JSON fails the size check before any parsing occurs.
Hash check catches a same-size swap.

**Not mitigated:** a same-size swap *with* a regenerated hash
constant — see §3.2. The attacker would need to modify both files
in the published bundle, which is equivalent to shipping a
trojaned kindly release.

### 3.4 Threat: schema-passthrough exploitation

Unknown JSON fields ride through the load and reach somewhere they
shouldn't (catalog reader had this — Batch N S301).

**Mitigation:** Zod `.strict()` on `BuiltinKeyringSchema` and
`BuiltinPublisherSchema`. Unknown top-level or per-publisher fields
fail validation at load.

### 3.5 Threat: terminal injection via curated label

A maintainer (intentionally or via compromised PR) lands a publisher
entry with ANSI escape sequences in `label` or `description`.

**Mitigation:** display strings flow through `sanitizeForTerminal`
at render time (Batch M discipline). Schema only enforces length
and required-ness; render-side sanitize strips control bytes.

**Not mitigated:** a malicious label that's still readable but
misleading (`"kindly-official"` impersonating the real maintainer
team). PR review is the control here.

### 3.6 Threat: UX of upgrades

User installed kindly v0.13, then `setup trust add`'d a key. v1.0
ships the same key in the built-in registry. What happens?

**Behavior:** `setup verify` returns `trust_source: "local"` —
local wins. `setup trust list` shows the entry under "local" with
the user's chosen label, not the built-in label. No duplicate.
This is the legitimate "user added it before we curated it"
upgrade path; producing it does **not** error.

**Reverse direction:** v1.0 user sees the built-in entry, then runs
`setup trust add` on the same publisher's key. Errors with
`BUILTIN_KEY_ALREADY_TRUSTED` — the user already trusts the key
through the built-in path; no local roster entry is needed.

**Removal:** `setup trust remove <built-in-id>` errors with
`BUILTIN_KEY_NOT_REMOVABLE`. Built-in keys are managed by kindly
upgrades. Removing a built-in key requires editing
`data/keyring/publishers.v1.json` + rebuilding the hash — a
maintainer-side operation, not a user-side one.

## 4. Curation policy

This section governs what gets into `data/keyring/publishers.v1.json`
during v1.0 alpha and beyond.

### 4.1 What gets in

A publisher key is eligible for the built-in registry when **all** of:

1. The publisher has signed at least one Setup that the kindly
   maintainer team has reviewed and accepts as a starter.
2. The public key is published at a stable, attributable URL (GitHub
   profile, project README, mailing-list archive). The URL goes in
   the entry's `references[]`.
3. The label is a human-readable name (publisher's GitHub handle,
   project name) — not an anonymous placeholder.
4. The PR adding the entry is reviewed by ≥ 2 maintainers and the
   hash is regenerated atomically with the JSON change (CI gate
   enforces).

v0.13 ships the file with `publishers: []`. The empty roster is the
**zero-curation** baseline; no decisions have been pre-loaded.

### 4.2 Removal procedure

A publisher key is removed when **any** of:

1. The publisher requests removal (key rotation, project handover).
2. The key is suspected compromised (publisher report, evidence in
   the wild).
3. The maintainer team's review reveals the curation criteria were
   not met.

Procedure:
1. Edit `data/keyring/publishers.v1.json` — drop the entry.
2. Run `bun run scripts/build-builtin-keyring.ts` — regenerates
   `BUILTIN_KEYRING_HASH`.
3. Commit both files atomically. CI gate verifies hash matches.
4. Tag a release. Users who upgrade get the removed key dropped
   from their built-in roster.

Users who installed the publisher's setups before removal keep
those setups working — `apply` does not re-verify post-install.
Users who attempt to import a setup signed by the removed key after
upgrading get `UNTRUSTED_SIGNER` and must use
`--accept-untrusted-signature` or `setup trust add` the key locally
if they accept the risk.

### 4.3 No revocation protocol in v1.0

There is no separate revocation list, no online check, no
key-recency requirement. Removal is "drop the entry, ship a
release." This is acceptable for v1.0's built-ins-only scope — the
maintainer's release cadence is the trust horizon. v2.0 user-
authored T2 will need a real revocation story.

## 5. Forward compatibility

### 5.1 v2.0 — user-authored T2

When user-authored Setups land, the trust roster becomes a
3-source structure:

| Source | Where | Mutation |
|---|---|---|
| Built-in | `data/keyring/publishers.v1.json` | Maintainer-curated, ships with release |
| Local | `~/.kindly/trusted-keys.json` | User-managed via `setup trust add/remove` |
| Pinned (TOFU) | `~/.kindly/pinned-keys.json` (TBD) | First-encounter pin with user prompt |

The `signerTrust` producer's API does **not** need to change. Add a
third lookup; extend `trustSource` to `"local" | "builtin" | "pinned"`.
The `BuiltinKeyringSchema` does not need a major bump — it's still
a curated commit-in-source list.

Removal procedure at v2.0 stays maintainer-side for built-in;
becomes user-side via `setup trust remove` for local; becomes
explicit unpin via `setup trust unpin` for TOFU.

### 5.2 Schema evolution

`kindly_builtin_keyring: "v1"` is a version axis, not a content
hash. v2 (if ever) would change the **shape** of the file — e.g.
embedding a revocation list, key-rotation trail, or metadata for
decentralized verification. v0.13 → v1.0 → v2.0 keys all stay
under v1 unless one of those structural changes lands.

`refuses unknown majors` is the policy: a future kindly that sees
`kindly_builtin_keyring: "v2"` while not understanding v2 fails
load (Zod `.literal("v1")` rejects). This mirrors the local
roster's `kindly_trust: "v1"` discipline.

## 6. Operational notes

### 6.1 CI

Required CI step (post-implementation):

```yaml
- name: built-in keyring hash invariant
  run: |
    bun run scripts/build-builtin-keyring.ts
    git diff --exit-code src/setup/builtinKeyringHash.ts
```

A diff means the JSON was edited without regenerating the hash —
CI fails, PR cannot merge.

### 6.2 Smoke tests (v0.13 ship)

End-to-end sanity check after install:

1. **Empty-roster verify:** `kindly setup verify --json <archive>`
   on any signed archive returns `trust_source` absent (key not in
   built-in or local). No error.
2. **Tamper detection:** edit `data/keyring/publishers.v1.json`
   without regenerating hash. Run any setup command — expect
   `BUILTIN_KEYRING_HASH_MISMATCH`, no fallback.
3. **Hash regen idempotence:** `bun run scripts/build-builtin-keyring.ts`
   twice. Second run is no-op (`git diff` empty).

### 6.3 v1.0 alpha curation checklist

Before tagging v1.0:

1. Maintainer signs starter Setups with their committed public key.
2. PR adds a `BuiltinPublisher` entry — `key_id`, `public_key_b64`,
   `label: "<maintainer-handle>"`, `description`, `since: "v1.0.0"`,
   `references[]`.
3. CI hash-rebind step regenerates `BUILTIN_KEYRING_HASH`.
4. ≥ 2 maintainer reviews on the curation PR.
5. Tests confirm `setup verify --json` reports `trust_source:
   "builtin"` for archives signed by the included keys.
